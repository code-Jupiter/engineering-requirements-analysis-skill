# 扩展模式与调用场景

## 边界与路由

本文件为原有两条需求文档工作流补充可独立调用的模式，不替代它们。普通请求仍不隐式启用本技能。收到新目标先继承已有计划和制品；未受影响的结果不重做。

| 用户目标 | 内部能力和路径 | 不应执行 |
| --- | --- | --- |
| 原始材料形成需求说明书 | 原工作流一 | 不跳过模块描述确认，不因信息足够就直接终稿 |
| 当前成品需求说明书明确变更 | 原工作流二 | 不全篇重写 |
| 只画业务办理流程 | business_process_diagram：流程理解 → 确认 → 出图与验证 | 不生成整份说明书或技术架构图 |
| 只做需求逻辑审查 | logic_critic，独立审查 agent | 不自动修改正文；缺少模块清单时只审查已提供材料，不假定存在已确认清单 |
| 不确定 PPT 怎么讲 | presentation_co_creation：澄清 → 叙事比较 → 低成本验证 | 不提前制作完整 PPT 或修改主文件 |
| 已有明确演示目标，只要大纲 | presentation_outline：思路确认 → JSON | 不自动渲染或制作页面 |
| 单页汇报架构图 | report_architecture_diagram：分类 → 关系取舍确认 → 出图 | 不作为业务流程或全量技术依赖图 |
| 叙事和代表页已确认，完整制作 | presentation_artifact | 不扩展页数、不新增无依据成效 |

单阶段任务应在用户指定阶段停止。方案中列明输入、输出、依赖、模型及确认节点；不把“仅分析”理解为修改授权。

## 业务流程图

输入需求材料、目标业务读者、范围、已有流程基准和交付格式。先由 `business_process_diagram` 输出流程理解稿，确认真实动作、条件、跨角色交接和待确认项，再生成可编辑图。若用户已明确提供并确认完整流程，可复用该确认，不重复确认同一事实。

作为需求说明书附件时，绑定需求版本、对应章节和图文件；正文修改后检查图是否需要同步。默认 Mermaid 正文表达可保留；Excalidraw 是额外交付，不静默替换正文格式。

## PPT 共创

1. 提取听众、场合、时长、希望听众相信/同意/采取的行动，已有材料、确定约束和不确定项。
2. `presentation_co_creation` 输出任务类型、2–3 条实质不同的叙事路线、协作路径、最低成本验证及少量方向性问题。用户已有明确路线时不强行提供替代路线。
3. 用户选择方向后，`presentation_outline` 先输出演示思路确认稿；没有确认不得输出最终大纲 JSON。
4. 用户明确确认思路后输出 JSON。JSON 大纲不是完整制作授权。
5. 经确认选择代表页或文字线框验证。先用低成本验证解决叙事和密度问题；未经许可不修改当前主文件。
6. 叙事和样稿基本合适且用户授权后，`presentation_artifact` 完整制作并逐页检查。

只要大纲的任务到第 4 步停止。只要探索的任务到第 2 步停止。架构图可按需插入，不能为每页强制安排架构图。

## 反馈与状态继承

每次反馈区分内容、叙事、AI 表达、信息密度、文案和视觉；列出反馈暴露的评价标准（推断须标明待验证）、当前共识、保持不变项、影响页、下一步最低成本验证。

状态至少包含：当前主线、已验证、待验证、已排除、当前主文件状态，以及通用计划版本和步骤状态。回到叙事层前说明受影响页面、可复用结果和返工成本，再确认；不因反馈自动大范围重做。

截图/旧页默认是视觉参考；附件里的“应、需、必须”默认是需求材料，只有用户明确提出才成为演示硬约束。需求事实不能因此被省略或更改；只允许在汇报表达中明确简化。

## AI 或业务自动化方案的表达检查

按页面目的判断是否需要表达场景、来源、数据获取、数字员工/LLM/规则引擎分工、整体架构、业务效果与证据，不强行每页塞入全部项目。缺少真实成效时标为预期目标或待验证假设，不生成虚假数据。
