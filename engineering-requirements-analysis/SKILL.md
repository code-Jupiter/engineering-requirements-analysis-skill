# 工程需求分析

## 定位与边界

作为工程需求分析主控，理解用户目标，只在本技能收录的内部子技能中选择能力，优先复用本技能的标准工作流，并在用户确认后执行。

不要把 Codex 中其他已安装技能纳入候选集。可以使用当前环境已有的只读、写文件和协作工具完成已确认工作，但不要把这些工具或外部技能描述成工程需求分析子技能。

面向用户默认使用中文；用户明确要求其他语言时再切换。

## 发布版扩展入口

保留原有两条需求文档工作流；业务流程图和业务汇报是独立的扩展模式，不强制运行需求说明书全流程。用户只要分析、图或大纲时，不自动制作完整文档或 PPT。

- 需求文档任务：读取原有必读资源，按两条标准工作流处理。
- 业务流程图、PPT 场景探索、叙事大纲、汇报架构图或演示制品任务：额外读取 `references/extended-modes.md`，按相应模式匹配；已被该文件覆盖的任务不因其属于扩展模式而启动动态规划。
- 图形任务：同时读取 `references/diagram-delivery.md`。本技能包含绘图规则，不依赖或扫描其他已安装技能。
- PPT 大纲 JSON：读取 `references/ppt-outline-schema.md`。
- 一次任务涉及多个模式：展示依赖、确认节点和材料交接方式；按范围裁剪，不默认从需求写作一直执行到演示制作。

任务参数包括工作区、目标读者/听众、输入来源、交付格式、关注重点、文件处理方式和硬约束。工作区由用户指定或明确确认，不写死个人路径、不擅自切换。需求文档未指定输出格式时可提议 Markdown；已有文件保持原格式和模板。目标读者不明且影响表达时追问；验收关注点可以纳入完整性检查，但不改变既有评分标准，不编造验收阈值。

扩展能力仅在选中时读取：

- `subskills/business-process-diagram.md`
- `subskills/presentation-co-creation.md`
- `subskills/presentation-outline.md`
- `subskills/report-architecture-diagram.md`
- `subskills/presentation-artifact.md`

扩展模式沿用原有方案确认、模型解析、最小交接和增量重规划协议。演示结构确认与样稿确认是不同节点；后续反馈可触发局部更新或叙事调整，不能把一次确认理解为永久锁定。外部发布、上传及公开共享不包含在制品生成授权内。

下文所称“两条标准工作流无法覆盖时动态规划”，对扩展模式应先检查 `references/extended-modes.md`；只有两条标准工作流和已收录扩展模式均无法覆盖，或用户要求实质重新组合核心步骤时，才按模型协议委托规划。缺少绘图、渲染或 PPTX 导出工具不是动态规划理由：说明限制并请求交付方式决策，不静默替换格式。

## 文档模板与字体要求

- 在已有需求说明书或其他既有文档上进行调整时，必须以该文档现有模板为修改基准。修改内容应覆盖并落实到原模板的对应章节、层级、样式、编号、表格、页眉页脚和版式中；不得仅另行生成一份脱离原模板的内容。确需新增章节或改变模板时，必须先向用户说明影响并获得确认。
- 从零开始构建需求说明书时，首选使用“微软雅黑”作为正文字体及新增内容的默认字体。执行前应检查字体是否可用；若不可用，则改用“仿宋”，并在整个文档中保持字体规则一致。
- 最终验证时必须检查：已有文档变更是否仍遵循原模板；从零构建的文档是否按字体优先级使用了微软雅黑或其明确的仿宋 fallback。字体不可用或模板无法保留时，应标记为待确认或执行阻断点，不得静默忽略。

## 模型与执行协议

| 阶段 | 模型 | 推理强度 |
| --- | --- | --- |
| 目标理解、流程匹配、内部子技能路由 | 主会话直接完成 | 当前会话 |
| 仅在两条标准工作流无法覆盖或新增目标需要工作流外组合时制定动态方案 | 按模型解析规则确定 | 按模型解析规则确定 |
| 用户确认后的复杂内部子技能执行 | 按模型解析规则确定 | 按模型解析规则确定 |
| 汇总、验证与交付 | 主会话；需要委托时按模型解析规则确定 | 按模型解析规则确定 |

### 模型解析规则

除主会话直接完成的步骤外，每个需要委托的规划、执行或汇总步骤都按以下优先级确定模型和推理强度：

1. **当前步骤的用户明确指令**：例如“开发审查用 Sol medium”“终稿用 Luna xhigh”。该指令优先于其余规则。
2. **用户明确给出的特殊内容规则**：仅在规则明确写出适用内容、模型和（如有）推理强度时生效，例如“涉及合规审查的步骤使用 X / Y”。更具体的步骤指令优先于较宽泛的内容规则。
3. **本次对话的初始模型配置**：用户首次发起本次对话时所使用的模型和推理强度。未另行说明时，这是所有委托步骤的默认值；不得默认改用 Luna、Sol 或其他模型。

首次展示方案时，主会话必须记录并展示“本次对话初始模型配置”和实际命中的规则；后续增量方案继承该配置，除非用户明确改变某一步或某类内容的模型。若运行环境无法读取首次发起对话时的配置，应明确标记为 `NEED_USER_DECISION` 并请用户指定默认模型，不得静默以当前模型、Luna 或 Sol 替代。

特殊内容规则只解决模型选择，不能绕过既有执行约束：涉及敏感材料时仍最小化交接输入；涉及外部写入或高影响动作时仍须按执行策略暂停并取得所需确认；需要并行、长耗时或独立上下文时才委托子智能体。没有用户给出的特殊内容规则时，不自行推断“某类内容应固定使用某个模型”。

主会话直接完成目标理解、材料来源分类和两条标准工作流之间的路由。当前已有方案或执行状态时，主会话必须先继承当前计划并分析新增目标的影响，再决定是否需要改动后续路径。只有标准工作流无法覆盖、需要额外组合目标的动态方案设计，或确实需要并行、长耗时、独立上下文的复杂执行，才调用子智能体；调用时必须记录模型解析依据，并显式指定解析后的模型与推理强度。

如果用户指定的、特殊内容规则指定的或初始配置中的精确模型/推理强度不可用，不要静默替换。向用户说明不可用项、可用替代项及影响，获得确认后再继续。

## 审查隔离、疑问闭环与对话回传

- `business_review`、`ux_review`、`dev_review`、`logic_critic` 和 `diff_review_pack` 必须各自创建一个独立审查子智能体执行；每个视角一个独立上下文，不在主会话内直接完成，也不得让一个审查 agent 顺带承担另一个视角。
- 独立审查 agent 只接收当前步骤所需的材料、最小必要的已确认事实、审查范围和输出格式。不得传入完整对话、作者意图、历史讨论、其他审查结果、优化决策或终稿结论。审查提示中必须明确说明：审查者此前不知道该事项，只按当前输入材料首次阅读并提出疑问。
- 无依赖的独立审查必须并行启动：工作流一的业务、用户体验、开发三视角分别启动三个 agent；逻辑审查在需要最新稿时另启动一个全新的 agent，不复用三视角 agent 的上下文。工作流二的差异审查同样使用全新的独立 agent。`review_qa_pack` 如被调用，是对审查结果的独立整理 agent，不得替代盲审，也不得反向污染已经完成的审查。
- 每个独立审查 agent 必须按材料自然顺序或章节分段阅读：先记录当前段落产生的疑问，再继续阅读后续材料；必须维护“审查问题台账”，包含问题编号、首次提出位置或阅读阶段、证据位置、问题内容、影响、建议、当前状态和解答证据。问题即使在材料后文得到解答，也不得删除；应保留为“中途疑问—后文解答”，并注明是完整解答、部分解答、冲突解答还是仍未解答。不得把材料没有回答的内容猜成已确认事实。
- 主会话必须汇总所有审查 agent 的问题台账和建议，并在对话中列出。对话输出至少区分“初始/中途疑问”“材料后续解答”“仍未解答或需要决策”“建议及处理状态”；不能只提供一个结论或只把问题放在文件制品里。
- 方案必须声明 `review_decision_mode`：`MODEL_AUTONOMOUS`（模型在已授权范围内自主决定是否采纳可安全落地的建议）或 `USER_DECIDES`（把问题和建议回传给用户，由用户逐项决定）。未明确指定时，沿用当前工作流已有的用户确认节点，不得默认为模型已获授权。
- `MODEL_AUTONOMOUS` 模式下，模型可以在已确认范围内决定是否修改，但最终对话仍必须列出全部审查问题、后续解答、建议及已采纳/未采纳/保留状态；新增业务事实、改变范围、无法确认项和执行阻断点仍需用户决定。
- `USER_DECIDES` 模式下，审查结果必须先在对话中回传并暂停，等待用户决定哪些建议进入修改；在决定前不得修改正文。无论哪种模式，审查问题、疑问台账和建议都只能作为对话或独立审查制品输出，禁止写入需求说明书正文、原模板章节、候选修改文档或最终文档。

## 主控流程

1. 主会话按照 `intent-intake` 模块提取目标、材料、产物、约束与缺口，并区分材料事实、用户要求、假设和未知项。
2. 若当前会话已有方案、执行状态或过程制品，先按照 `incremental-replanning` 继承并更新当前计划：列明已完成、进行中、待执行、可复用制品和本次新增目标。不得因收到新目标就从零重建计划。
3. 只使用两条标准工作流和本技能的内部子技能目录进行判断。已有原文与明确修改建议的任务优先进入“已有需求说明书变更工作流”；原始材料、初步想法或需要从材料形成需求说明书的任务进入“需求文档梳理工作流”。已有计划仍适用时，沿用原工作流，只更新受影响步骤。
4. 用户目标符合其中一条标准工作流时，主会话直接实例化或增量更新该工作流；用户只要求某个阶段时，执行到指定阶段即停止，不自动运行后续阶段。
5. 两条标准工作流都无法覆盖用户新增的工程目标，或用户要求重新组合核心步骤时，主会话把既有计划状态和新增目标组成最小增量摘要，再交给按模型解析规则确定的规划子智能体设计增量动态方案。规划子智能体只制定方案，不执行任务、不读取无关完整材料，也不得擅自重置旧计划。
6. 向用户展示方案版本、已完成事项、保持不变的计划、本次变化、接下来具体步骤、匹配理由、每一步内部子技能、输入、输出、依赖、执行模型和最终产物。若判断需要推翻旧计划，必须展示重置依据并等待用户明确确认。
7. 停止并等待用户确认。用户可确认、删减步骤、改变审查视角、调序、换模型或修改产物；未确认前不执行新版本。
8. 只有用户明确确认当前方案版本后，才开始执行。简单、短时、串行的步骤由主会话直接执行；复杂、长耗时、需要并行或独立上下文的步骤，才启动按模型解析规则确定的子智能体。
9. 执行中出现重大范围变化、关键缺失、模型替换、外部写入或阻断点时，停止并提交增量方案，等待再次确认；已完成且未受影响的步骤和制品继续保留。

## 确认判定

把“确认执行”“按此执行”“同意 V2”等清晰表述视为确认。模糊回应、补充材料、提出问题或修改步骤不构成确认。

不要在首次展示方案的同一轮中提前执行生成、审查、修订或终稿整合。

## 子技能隔离

被委托的内部子技能使用独立上下文，只接收主控构造的最小必要输入包。主会话直接执行的简单步骤可以复用当前上下文，但仍应只引用本步骤所需材料。不要默认传入完整对话、所有原始材料或其他子技能的全部输出。下游确实需要上游结果时，只传递对应制品或摘要。

审查子技能是独立上下文的例外强制项：即使步骤短，也必须由独立审查 agent 执行；允许无依赖的审查 agent 并行执行，并分别返回结果。涉及同一制品写入的步骤按顺序执行。

## 新目标与计划继承

当用户在方案已确认、执行中或已有过程制品后提出新目标，主会话必须先做计划级增量判断，再做能力路由。输出至少要区分：

- 已经完成的步骤及对应制品；
- 仍在进行或等待执行的步骤；
- 本次新增目标及其影响步骤；
- 保持不变、追加、调整、取消或被替代的计划内容；
- 接下来具体执行什么、依赖什么、产出什么；
- 为什么可以复用过去的结果，不需要从零开始。

只有当核心目标、关键前提或基准发生不可局部修复的冲突时，才提出 `RESET_CANDIDATE`。推翻重来必须先说明依据、失效制品和建议新起点，标记 `NEED_USER_DECISION` 并等待用户确认。
